# Workflow

This page describes the path of a change from the roadmap to the merge. The binding short version is in the project's [AGENTS.md](../kit/common/AGENTS.md); this page holds the why and the handling of edge cases. Who has which role is in [roles.md](roles.md), how to brief Codex in [codex-briefs.md](codex-briefs.md). Every issue gets its own session, which takes it to the merge; its prompt is [issue-session.md](session-briefs/issue-session.md). A PR that no session is working on any more is finished by a maintainer session ([maintainer-session.md](session-briefs/maintainer-session.md)).

## From plan to issue

The owner maintains the roadmap ([docs/roadmap.md](../kit/common/docs/roadmap.md)): a goal, below it milestones, below them the issues. The milestones are the priority; within a milestone the list order of the roadmap applies. There is no task list in a file and there are no status documents; the state of a task is its issue, its branch and its PR (GitLab: MR).

## The issue is the specification

A task is an issue, written as a spec following the issue template ([GitHub](../kit/github/repo/.github/ISSUE_TEMPLATE/task.md), [GitLab](../kit/gitlab/repo/.gitlab/issue_templates/Default.md)). In the project the sections are named in English and have fixed jobs:

- **What**: the problem or capability in plain words. If the issue traces back to a decision of the owner, it is quoted here verbatim, followed by two sentences on the capability.
- **Why it happens**: only for defects and gaps. The current state as a list, each line with a file reference (`path/file.ext:120`), checked against the current main branch. For new capabilities the section is omitted.
- **Proposed change**: the smallest change that solves the problem, with file names and a note on what is reused ("no new mechanism, the existing one is used", design rule 9). Numbered steps when the order matters.
- **User check**: what a user does and then sees, in their words and with concrete values that come from the domain (law, standard, an invoice worked out by hand), never from the implementation; plus who checks: `agent` or `owner` where no agent can get. Omitted when no user notices the change. Details in [acceptance.md](acceptance.md).
- **Acceptance**: checkboxes with concrete, verifiable statements. The usual ones: scenario red first, unit tests red first, existing behavior unchanged (existing tests stay green without modification), the project's hard invariants hold for every changed route, docs in the same PR, the proof of the UI per the project's AGENTS.md for visible UI, `make test` and `make lint` green.
- **Out of scope**: what the issue deliberately does not do, each with the place where it belongs (issue link). Irreversible operator steps such as activating a production instance belong here: the owner performs them with the runbook, and they are never tested against the production database.

Security-relevant issues begin with "Security-relevant.". An issue is cut so that a session with 64k context can read, implement and check it; anything bigger is split and sorted into the roadmap.

## Sharpen the spec, ask questions

Before work begins, the issue session sharpens the spec against the code: do file references and numbers still hold, which existing mechanism is reused, who reads each new field? It records deviations as a comment on the issue.

If a decision is needed that only the owner can make, it asks the questions as an issue comment: numbered, for each question the options (a), (b), (c) and a recommendation. It does not wait for the answer. If the rest can be implemented without it, the comment says so ("the rest is implemented without the answers, the PR follows as `Refs #N`") and the session implements it; otherwise it releases the issue and hands over the next unblocked one. Anyone who abandons an issue before the PR first writes a comment that begins with `Blocked:` and the reason; until a later "Owner decision" follows, no session takes the issue up again, otherwise the chain would restart it over and over. The owner answers as a comment on the issue or PR headed "Owner decision", numbered per question. A decision that arrives via the owner or the parent session is published there first and then implemented. It is then implemented by a session with empty context: an issue that is still free is taken by an issue session of the chain as soon as it is no longer blocked; an open PR that waited for the answer is finished by a maintainer session that the owner starts. Open questions and tasks of the owner outside the code (DNS, servers, platform switches) never block; they appear as "For the owner" in the PR.

## Red first, then the smallest change

The tests come first, and they fail with the intended failure: the scenario for the happy path as Gherkin in `features/` (see [features/README.md](../kit/common/features/README.md)) and the unit tests for edge and error cases in the area's existing test file. If the project has no Gherkin, unit tests suffice. Then comes the smallest change that turns them green, afterwards refactoring with green tests. The PR states the evidence that the tests were red beforehand.

The change follows the design rules of the [AGENTS.md](../kit/common/AGENTS.md): one source of truth, no configuration keys for tuning numbers, no field and no parameter without a reader in the same PR, errors by structured codes instead of by message text, what exists before what is new. The scope is the acceptance list, nothing less and nothing unasked more. A finding outside the scope becomes a new issue, never code. Progress is code, tests and a commit. No state, contract, receipt, handover, evidence, hash or audit files are created, no repair or review chains that pass such files along, and no new plan, log or status documents. Decisions live in the issue, in the PR description or, if they bind future work, as an ADR under `docs/adr/`.

## Checks before the PR

Before the push, an adversarial pass runs over the diff: the `verifier` (Opus) is to refute the work, not confirm it, and delivers a verdict with a concrete failure scenario. Its findings are fixed before the PR opens. In addition come `make lint` before every push and the targeted tests of the area. The whole suite (`make test`) can take very long; it runs in CI and before the merge. Gates that CI cannot run (for example a build that needs macOS) run locally on exactly the pushed state; the PR names SHA and result, and the session that merges repeats them on the SHA it merges. Docs change in the same PR under the documentation contract of the AGENTS.md, and for UI changes DESIGN.md as well.

## PR and commits

The PR body follows the template ([GitHub](../kit/github/repo/.github/PULL_REQUEST_TEMPLATE.md), [GitLab](../kit/gitlab/repo/.gitlab/merge_request_templates/Default.md)): what the change is for, which scenarios and tests were red first, the checks, for changes to something a user sees the evidence that the project's AGENTS.md requires (web: screenshots before and after at desktop width and at 360 px; app: simulator screenshots of the changed views; without a UI: the changed output), captured with synthetic data and never in production, and notes for the reviewer. `Closes #N` appears only when every acceptance box is met, otherwise `Refs #N` and what is still missing. The session pushes only its own branch and merges only its own PR, only after the fresh review (see "Review and merge"); it never pushes to the main branch. Codex and subagents never push or merge.

Commits are named `type(scope): lowercase summary in the imperative`, about 70 characters, for example `fix(import): skip duplicate rows`. The body states cause, change and tests and ends with `Refs #N` or `Closes #N`. There is no attribution anywhere: no Co-Authored-By line for an assistant, no "Generated with", no mention of AI or agents as author, neither in commits nor in PRs, issues, comments, code or docs.

## Stacked branches

If a PR depends on one that is not yet merged, its branch is forked from the branch of the base PR. The PR targets the branch of the base PR (or, with a note, the main branch) and says "stacked on #M" in the body. Migrations in a stack are numbered in sequence and shift when the base changes. Stacks are merged from bottom to top. While the base is open, the session of the dependent PR pulls in the base's branch, not the main branch. The base's session merges without deleting its branch, retargets the dependent PR to the main branch and only then deletes the branch. The session of the dependent PR asks for this merge every ten minutes, for at most an hour (if the base carries "Not merged", is parked or closed, the session ends at once), then merges the main branch into its branch, renumbers migrations and merges itself. If it ended earlier with "Not merged" because the base was missing, the base's session starts a maintainer session for the dependent PR after its merge.

## Worktrees

Every session works in its own Git worktree outside the main checkout with a predictable name: `<repo>-issue-N` for an issue, `<repo>-review-N` for a PR that a maintainer session takes over. A worktree lives exactly as long as its PR and belongs to the issue or PR, not to the session that created it, because that session is long over at the merge. As soon as the PR is merged or closed, the session that notices this checks that the tree is clean and nothing is still running there, after a merge also that it has arrived in the main branch, and removes it together with the local branch: `git worktree remove <dir> && git branch -D <branch>`. As a rule that is the session that merged: it removes the issue worktree of the merged PR, a maintainer session also its review worktree. In addition, every new session clears away, before starting, the worktrees of its kind whose PR is done. A worktree `<repo>-issue-N` in `git worktree list` of the main checkout also shows that issue N is being worked on; therefore the issue session creates it first of all, before it reads or comments. The review worktree is detached on `origin/<branch>`, because Git checks out a branch in only one worktree and the issue worktree holds it. Without this rule, dozens of worktrees and many gigabytes pile up within a few weeks that nobody can account for any more.

## Cleanup

Every agent cleans up after itself. What a session creates, it removes again at the end of its task:

- Git worktrees and local branches, as soon as the PR is merged or closed (see above);
- Compose projects of acceptance or verifier runs, completely: containers, volumes, networks and the project's own locally built images (`docker compose -p <name> down -v --rmi local`), never production and never the shared test database;
- scratch directories with briefs, logs, screenshots and reports, as soon as their content is in the issue or PR;
- background processes it started (dev servers, watchers, browsers, test runs);
- lock files it holds, as soon as none of its own processes needs them any more.

Before starting, the session checks for leftovers (`git worktree list`, `docker compose ls`, its own scratch directory, its own processes) and cleans up first. It removes only what it created itself, with one exception: issue and review worktrees with a merged or closed PR (see above). All other leftovers of other sessions or of the owner it reports instead of deleting. Without this rule, disk and Docker fill up with leftovers that nobody can account for any more.

## Migrations

Only for projects with a migration chain; the others omit the section in their AGENTS.md. An already committed migration is never changed; every change is a new revision. Per migration chain only one new revision is in progress at any time. In the same PR, the new revision becomes the release target everywhere: deployment target, deploy docs and upgrade tests move together. If another PR claimed the number first, the later one renumbers and says so in the body. Production moves only through a reviewed release.

## Shared test database

Only for projects with a shared test database or another exclusive test resource; the briefs give the project's rule as `{{LOCK_RULE}}`, and for isolated test resources it reads "none". A test database has exactly one writer. The make targets that use it acquire the mkdir lock `/tmp/<project>-testdb.lock` themselves and are therefore never wrapped in a second lock acquisition (deadlock). Direct test runs hold the lock in the same shell until the end. Nobody starts a database of their own or adds another Compose file. Production containers, volumes and databases, as the project's AGENTS.md names them, are never touched.

## One session, one task

A session works on exactly one issue, from claiming it to the merge of its PR. The next task gets a new session with empty context, never the same chat and never a fork of it: a fork carries the whole history. The reason is context. Every further task in the same chat pays for the entire history of the previous one again at every step, and what is still in the context is almost always irrelevant to the new task. An issue is therefore cut to 64k context; the session reads only the files the issue names, large files with `rg -n` and line ranges. Large documents, logs and diffs are summarized when needed by the local model (see [roles.md](roles.md)).

The sessions form chains that continue themselves. The issue session hands over the next unblocked issue of the milestone to a new session, either as soon as its PR is open (`<HANDOVER>` = `after PR`: the next issue is implemented while this one is reviewed and merged) or only after its merge or exit (`after merge`: exactly one issue is in progress at a time, slower but with no stacks and no parallel merges); with `<MILESTONE>` = `none` the chain has one link and the owner starts every issue (roadmap order; an issue is blocked if it has an open owner question about its core, a `Blocked:` comment without a later "Owner decision", a PR, a worktree `<repo>-issue-N`, a branch `issue-N` without a worktree, if it is the issue the session itself abandoned, or if its files are named by an issue that is in progress and has no PR yet; whoever needs the files of an open PR stacks on it). For this it fills in the prompt [issue-session.md](session-briefs/issue-session.md) and starts the new chat with it: in the Claude desktop app with the tool `start_session` (`initiation: "user_asked"`, `context: "fresh"`, no fork, `use_worktree: false` in the main checkout, because the session creates its worktree `<repo>-issue-N` itself; this is also why the owner starts the first session in the main checkout without an app worktree); otherwise it names the issue in its report and the owner starts the chat with the brief. It hands over early and not only after the merge, so that the chain keeps going while it waits for CI and review; afterwards it stays with its own PR until it is merged or a fixed exit applies. The owner starts only the first session of a chain.

Waiting is bounded and never on the owner. For CI the session waits by polling at intervals, for the merge of a stack base at most an hour, for a held lock at most its maximum duration plus five minutes, with one attempt every five minutes. If the merge needs the owner (a user check `owner` that the owner has not yet confirmed, an open owner question without whose answer the PR would not be correct), it does not wait at all: it writes the state as a comment "Not merged" on the PR, cleans up and ends. Items "For the owner" that the merge does not need (DNS, platform switches) do not hold it up. A PR with the label `parked` is parked; only the owner sets and removes that label, and a session that sees it ends without merging. If the owner rejects a PR or its scope ("Owner decision: close"), the session closes it, writes a `Blocked:` comment on the issue and ends. A PR that no session is working on any more (it waited for the owner and the owner has answered, it was parked and has been released, it is a stack member whose session ended before the base merged, its session was aborted, or it comes from outside the kit) is finished by a maintainer session; it starts no successor session. As a rule the owner starts it by hand; an orphaned stack member is started by the base's session after its merge.

Several issue chains may run in parallel if the owner starts them and their issues do not touch the same files; each session merges its own PR, stacks from bottom to top. All sessions of a project run on one machine, because the locks under `/tmp` and the worktree claims apply only there. The merges themselves run one after another: immediately before it updates the branch with the main branch and merges, the session takes the lock `/tmp/<project>-merge.lock` (a `mkdir`, PR and time in `info`), and it releases it as soon as the merge has arrived in the main branch, pinned to the SHA on which CI and the local gate were green. That way the state CI checked is the same one that lands in the main branch, and no lock hangs on a session that is waiting for review, acceptance or the owner. The maximum duration of a lock is twice the duration of the suite plus 30 minutes (`<LOCK_MAX>` in the briefs); whoever reaches it releases the lock and ends without merging. A lock whose time is older than this maximum duration, or one that names an already merged or closed PR and is older than 30 minutes, is the leftover of a crash; the session removes it atomically (`mv` to a name of its own, check `info`, then `rm -r`) so that two sessions do not delete a fresh lock at the same time. Any other lock is removed only by the owner. If the acceptance environment is not separate per run (shared staging, fixed ports), an acceptance run holds `/tmp/<project>-acceptance.lock` under the same rules. Sessions send each other no messages: everything another session needs to know is a comment on the issue or PR. The procedure in detail is in the prompts.

Every session is named after its issue, `<project> #N: <issue title>` for the issue session and `<project> #N: review PR <M>` for a maintainer session, so the sidebar groups them by issue; a maintainer session binds its PR to itself, and with the desktop app's setting "Auto-archive sessions when their pull request closes" both sessions of an issue are archived once the PR is merged or closed.

Whoever starts a session stays connected to it in the desktop app: the app wakes the starter at every end of a turn of the started session and sends its whole context again in the process, and it keeps a list of all connected sessions up to date in it. A planning chat of the owner that starts many sessions thus pays its entire history again for every finished session. Therefore two rules apply. Every session detaches itself from its starter as the very first thing with `detach_session` (`session_id: "self"`), and whoever starts a successor session detaches it right after the start; a detached session reports nothing more to its starter. And the chat in which the owner plans and talks to Claude starts no working sessions: at most it fills in the brief; the first session of a chain is started from a new, empty chat (paste the brief) or from a chat that does nothing else. If the app nevertheless reports the end of its successor session to a session, it ignores that as long as it is still working on its PR, and after its report it answers with one line without tool calls.

## Acceptance from the user's side

Tests and review check whether the code does what the issue says; whether a user can cope with it is checked by the acceptance agent. Before the merge of a PR with a user check it runs blind on its state, per milestone across all core journeys in `docs/acceptance/journeys.md`, and the owner triages the findings. Without a passed user check there is no merge. Results appear as a comment on the PR or on the milestone, never as a file in the repository. Why this is necessary and how it runs is in [acceptance.md](acceptance.md).

## Review and merge

The session that wrote a PR never reviews it alone: whoever knows the intent reads it into the code. After opening the PR and the handover, it starts a `verifier` (Opus) with fresh context and a fixed prompt that contains only the worktree path and the numbers of PR and issue; the verifier reads diff, PR description, acceptance list and CI state itself with `gh` or `glab`, and it is to refute the change. It gets no summary, no justification and no expected findings. For risky changes a second one runs blind alongside. The session fixes the findings instead of explaining them away; a finding outside the acceptance list it turns into a follow-up issue, and one it considers wrong it refutes with a test of its scenario. Each round has one push and one comment on the PR, and each round gets a new fresh review; the own check before the PR does not count as a round. After the third review the scope is frozen (AGENTS.md, "Three rounds, then freeze"), at most two more rounds follow, and if after the fifth a finding still needs a push, there is no merge. The PR description names under "Notes for the reviewer" only what the diff does not show (stack and merge order, migration number, where the evidence lies), no risks and no "look at this first", since the `verifier` reads that too. Merging happens only with green CI on exactly the SHA that is merged, with the local gate on the same SHA, with a passed user check ([acceptance.md](acceptance.md)), with a scope equal to the acceptance list, without loosened tests and without sentences granting a one-time authorization in AGENTS.md, CONTRIBUTING.md or the rules, never by admin override, and only under the merge lock. A PR without an issue and without an owner decision, or with a scope rejected by the owner, is closed. The details are in the prompt [issue-session.md](session-briefs/issue-session.md); the maintainer session ([maintainer-session.md](session-briefs/maintainer-session.md)) reviews and merges an orphaned PR by the same rules.

Where someone else merges (`MERGE_BY=maintainer` in the project file, for a repository we contribute to), the session ends with a handover instead of a merge: same preconditions (CI and gates green on the head SHA, the last fresh review without an open finding, the user check passed), but no merge lock, no `pr merge`, and no comment on the issue or the PR at all; questions, outcomes and follow-up drafts go into its report. The branch is kept current by merging `origin/<main>` into it, never by rebase or force-push. If anyone else pushes to the PR or reworks it, the session stops at once. Stacks do not exist there, and successor issues come only from the owner's own (assigned to the owner, or opened by the owner without an assignee).
